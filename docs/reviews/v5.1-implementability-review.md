# 結論：**「設計書」としては利用可能だが、「実装ドキュメント」としては追加が1点必要**

率直に回答します。

## 1. 「このまま使える」部分（設計書として完成している領域）

### ✅ 実装判断に迷わないレベルで定義されているもの

| 項目 | 評価 | 理由 |
|:---|:---:|:---|
| **コア型の定義（7種）** | ◎ | `ARC_, O_, E_, ME_, A_, MY_, RF_` の境界が明確。新規ファイル作成時に「どの型か」で迷わない |
| **Frontmatterスキーマ** | ◎ | 必須フィールド、任意フィールド、値の取りうる範囲（enum）が明記されている |
| **状態管理の分離** | ◎ | `epistemic_status`, `review_status`, `document_status` が分離されており、状態遷移が一意に決まる |
| **ネタバレ制御** | ◎ | `disclosure` オブジェクトの構造が明確で、静的サイト生成での実装が可能 |
| **ディレクトリ構成** | ◎ | ファイルの配置場所が一意に決まる |
| **Lint仕様** | ◎ | チェック項目が列挙されており、バリデーションツールの仕様にそのまま使える |
| **非目標** | ◎ | やらないことが明確なので、スコープクリープが起きない |

**これらは「設計思想」レベルではなく、「実装仕様」レベルで書かれています。**

## 2. 「このままでは実装が止まる」部分（追加が必要な領域）

### ⚠️ 実装時に必要になる追加ドキュメント

#### ① **JSON Schema の実体（必須）**

設計書には「`schemas/common.schema.json` を作成する」と書かれていますが、**実体がありません**。

実装には以下が必要です：

```json
// schemas/claim.schema.json の例（実体が必要）
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["id", "type", "subject", "predicate", "object", "schema_version"],
  "properties": {
    "id": {
      "type": "string",
      "pattern": "^A_[^_]+_(alludes_to|analogous_to|recurs_as|structurally_matches|misreads_as|foreshadows|inverts|parodies|sublates)_[^_]+_ch\\d{4}$"
    },
    "type": {"const": "analytical_claim"},
    "subject": {"type": "string", "pattern": "^\\[\\[E_.*\\]\\]$"},
    "predicate": {"enum": ["alludes_to", "analogous_to", "recurs_as", "structurally_matches", "misreads_as", "foreshadows", "inverts", "parodies", "sublates"]},
    "object": {"type": "string", "pattern": "^\\[\\[(E_|ME_).*\\]\\]$"},
    "epistemic_status": {"enum": ["hypothesized", "supported", "confirmed", "disputed", "refuted", "sublated"]},
    "review_status": {"enum": ["unreviewed", "pending", "human_verified", "needs_revision"]},
    "document_status": {"enum": ["draft", "active", "archived", "superseded"]},
    "spoiler_after": {"type": "string", "pattern": "^ch\\d{4}$|^final$|^meta$"},
    "evidence": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["source_id", "locator"],
        "properties": {
          "source_id": {"type": "string", "pattern": "^SRC_.*$"},
          "locator": {
            "type": "object",
            "required": ["chapter"],
            "properties": {
              "chapter": {"type": "string", "pattern": "^ch\\d{4}$"},
              "lines": {"type": "string"},
              "quote": {"type": "string"}
            }
          }
        }
      }
    }
  }
}
```

**これが無いと、LintツールやObsidianプラグインのバリデーションが実装できません。**

#### ② **ファイル命名規則の詳細（必須）**

設計書には「正規ID」とありますが、**ファイル名との対応関係**が明記されていません。

例：
- `id: A_ハルベルト_alludes_to_アポロン_ch0124` の場合、ファイル名は？
  - `A_ハルベルト_alludes_to_アポロン_ch0124.md` ？
  - ハッシュ化する？ `A_a1b2c3d4.md` ？
- 日本語IDの場合、ファイルシステムでの挙動は？
- 衝突回避のルールは？

**これが無いと、ファイル作成・リネーム・リンク解決の実装が止まります。**

#### ③ **WikiLink解決ルール（必須）**

Obsidianの `[[E_char_ハルベルト]]` が、どのファイルを指すのかの解決ルールが必要です。

- `E_char_ハルベルト` → `wiki/entities/characters/E_char_ハルベルト.md` ？
- 同名異義語の場合（`E_char_ハルベルト` と `E_term_ハルベルト` が存在する場合）？

#### ④ **エージェントプロンプト契約（実装時に必要）**

設計書には「別紙化する」と書かれていますが、実装時には以下が必要です：

- `extraction_agent` が受け取る入力形式
- `extraction_agent` が出力するJSON形式
- `allusion_linker` が受け取る候補リストの形式
- `sublation_agent` が受け取る競合A_の形式

**これが無いと、エージェント実装が属人化します。**

### Phase 1: Lintツールの実装（1〜2日）

Pythonで `lint.py` を作成し、サンプルファイルがスキーマに準拠しているか検証する。

```python
# lint.py の骨子
import yaml
import jsonschema
from pathlib import Path

def lint_file(file_path: Path) -> list[str]:
    errors = []
    
    # 1. YAMLパース
    with open(file_path) as f:
        try:
            data = yaml.safe_load(f)
        except yaml.YAMLError as e:
            return [f"YAML parse error: {e}"]
    
    # 2. schema_version 確認
    schema_version = data.get("schema_version")
    if schema_version != "5.1":
        errors.append(f"Unsupported schema_version: {schema_version}")
    
    # 3. JSON Schema バリデーション
    node_type = data.get("type")
    schema_path = Path("vault/schemas") / f"{node_type}.schema.json"
    if schema_path.exists():
        with open(schema_path) as f:
            schema = json.load(f)
        try:
            jsonschema.validate(data, schema)
        except jsonschema.ValidationError as e:
            errors.append(f"Schema validation failed: {e.message}")
    
    # 4. 追加チェック（設計書のLint仕様に基づく）
    # - 死リンクチェック
    # - 証拠チェック
    # - ネタバレ境界チェック
    
    return errors

if __name__ == "__main__":
    for md_file in Path("vault/wiki").rglob("*.md"):
        errors = lint_file(md_file)
        if errors:
            print(f"❌ {md_file}")
            for error in errors:
                print(f"   - {error}")
        else:
            print(f"✅ {md_file}")
```

## 4. 最終評価：「設計書」としての完成度

| 観点 | 評価 | コメント |
|:---|:---:|:---|
| **設計思想の明確さ** | ◎ | 7コア型、状態分離、知識核とアダプタの分離が明確 |
| **データモデルの厳密さ** | ◎ | Frontmatterスキーマが具体的に定義されている |
| **実装可能性** | ○ | スキーマ定義・命名規則の詳細が追加で必要 |
| **保守性** | ◎ | Lint仕様、移行計画、非目標が明記されている |
| **拡張性** | ◎ | サブタイプによる拡張が可能 |

**結論：**
- **「設計書」としては利用可能**（実装の方向性・判断基準が明確）
- **「実装ドキュメント」としては、JSON Schema とファイル命名規則の詳細が追加で必要**
